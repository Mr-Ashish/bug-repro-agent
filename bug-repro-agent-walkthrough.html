§1 Background

The Problem

Open-source projects drown in bug reports. Plane — an open-source project management tool competing with Jira and Linear — has 791 open issues, of which 289 are bugs. Many of those bug reports are well-written, with clear steps to reproduce. But maintainers still have to manually walk through each one — launch the app, click through menus, type the right input, observe the failure — before they can even begin fixing it.

That manual reproduction loop is the bottleneck. It takes 5–15 minutes per issue, assumes a working local environment, and produces no reusable artifact. If the maintainer's setup differs from the reporter's, the bug may not even appear — and the issue gets tagged "cannot reproduce" and forgotten.

💡 Core insight: A bug report already contains the reproduction plan in natural language. An LLM can read those steps, drive a browser, and report what it sees — no per-issue scripting needed.

That's what repro-agent does. Given a GitHub issue URL, it fetches the bug report, injects it into a generic prompt template, launches a browser automation agent, and lets the LLM figure out the steps. The output: screenshots, an action log, a structured verdict (REPRODUCED / NOT_REPRODUCED / INCONCLUSIVE), a Playwright regression test, and a rich report posted back to the issue.

Identity: Reproducer, Not Fixer

This is a deliberate design constraint that shapes everything. The agent never proposes patches, never edits source code, never says "FIXED." Its job is strictly observational: execute the reported steps, capture what happens, and tell you whether the bug is real. This constraint exists because reproduction and repair require fundamentally different capabilities — and conflating them produces neither well.

VerdictMeaningExit Code
REPRODUCEDThe reported bug behavior was observed0
NOT_REPRODUCEDFeature worked correctly — bug not confirmed1
INCONCLUSIVEEvidence ambiguous — can't confirm or deny2
🔑 Why this matters: By constraining the agent to observation-only, we can trust its output without reviewing code changes. The verdict is a fact claim about what the agent saw, not a judgment about correctness. This makes the system useful even when the bug turns out to be "working as designed."

§2 Architecture

How does data flow from a GitHub issue URL to a posted verdict?

The system has four layers, each with a distinct responsibility. The key design decision: only one layer reasons about the bug. Everything else is infrastructure.

Notice that drive.py saves artifacts before closing the browser. This is intentional — the browser connection can hang if Chrome is unresponsive, but the agent history is already in memory. Artifacts survive crashes.

How does the verdict get parsed?

The agent is instructed to emit a structured line in its final message. drive.py scans backward through the output looking for this pattern:

📄 Verdict regex — scripts/drive.py
VERDICT_PATTERN = re.compile(
    r"VERDICT:\s*(REPRODUCED|NOT_REPRODUCED|INCONCLUSIVE)\s*\|\s*(.+)",
    re.IGNORECASE,
)

This is the entire verdict parsing logic — one regex. The simplicity is intentional: no per-issue matchers, no keyword extraction, no NLP. The agent is told the exact format to use, and the regex either finds it or defaults to INCONCLUSIVE. The verdict maps directly to an exit code, which the meta-agent (Grok) uses to decide what to do next.

§3 Code Walkthrough

Five Python scripts, each with a single job. No classes to instantiate, no framework to understand — just functions you can read top to bottom.

1 drive.py — The Brain 745 lines

One script does everything: fetch, prompt, drive, parse, save. This is the only file you need to understand to grasp how the system works.

💡 Design force: Why one script instead of a pipeline? Because each phase depends on the previous one's output in subtle ways — the prompt needs the issue body, the agent needs the prompt, artifacts need the history object. Splitting into separate processes would mean serializing intermediate state to disk, adding coordination overhead, and making debugging harder. For a hackathon project, colocation beats modularity.

CDP Auto-Discovery

Instead of hardcoding a WebSocket URL, drive.py hits Chrome's debug API to find the active session:

📄 scripts/drive.py · discover_cdp_url()
def discover_cdp_url(debug_port: int = 9222) -> str:
    """Auto-discover Chrome CDP browser-level WebSocket URL."""
    resp = urllib.request.urlopen(
        f"http://localhost:{debug_port}/json/version", timeout=3
    )
    data = json.loads(resp.read())
    ws_url = data["webSocketDebuggerUrl"]
    return ws_url

The Prompt Template

The generic template that works for any issue. The bug report body is injected as-is — the LLM interprets the steps:

📄 scripts/drive.py · TASK_TEMPLATE (simplified)
TASK_TEMPLATE = """Reproduce a bug in Plane (project management app).

## App
- URL: {plane_url}
- Credentials: {email} / <secret>
- Workspace: {workspace}

## Bug (issue #{number})
{title}
{body}

## Principles
- You are a reproducer, not a fixer.
- Navigate by URL when possible.
- Every step should advance the reproduction.
- Budget your steps.

## Verdict format
VERDICT: REPRODUCED | <what you saw>
VERDICT: NOT_REPRODUCED | <feature worked correctly>
VERDICT: INCONCLUSIVE | <why you couldn't determine>"""
🔑 The issue IS the plan. No per-issue scripting. No hardcoded click sequences. The raw issue body becomes the reproduction plan. This is the core bet of the project — and it works because modern LLMs are surprisingly good at parsing informal bug reports into actionable steps.

System Prompt Extension

The task prompt can get summarized during long runs (browser-use compacts message history). Critical instructions live in extend_system_message so they survive compaction:

2 seed.py — Environment Readiness 405 lines

Before the agent can reproduce anything, Plane needs to be running with test data. seed.py handles both verification (check) and setup (populate).

The PlaneAPI class uses only stdlib — no requests, no httpx. It authenticates via Plane's session cookie flow (same as the web frontend) and talks to the internal Django API. The seed data is intentionally crafted for edge-case testing:

⚠️ Watch out: seed.py talks to Plane's internal API at /api/.... These are not documented public endpoints — they're the same AJAX calls the React frontend makes. If Plane's API changes, seed.py breaks. This is fine for a hackathon, but a production tool would need a proper integration layer.

3 post_comment.py — GitHub Reporter 530 lines

Reads every artifact from reproductions/<N>/, builds a rich Markdown comment, and posts it to the GitHub issue. The comment includes embedded video, a step trace table, a smoking-gun screenshot, root cause analysis, and the Playwright regression test.

The trickiest part: image hosting. GitHub issue comments can't embed local files. The script commits the GIF, video, and evidence screenshot to the repro-agent's own repo, pushes, and uses raw.githubusercontent.com URLs. Crude but effective — every image is permanently linked.

✅ Password masking: The mask_password() function runs on every piece of text before it's written to the comment. Plane credentials (PLANE_PASSWORD) never appear in the GitHub comment, action log excerpts, or agent thoughts.

4 generate_playwright.py — Test Generator 230 lines

Converts the action log into a skeleton Playwright test. The login fixture works out of the box (handles Plane's two-step email → password flow). Post-login steps are dumped as structured comments — the meta-agent (Grok) rewrites them into real selectors and assertions.

This two-stage approach exists because browser-use's action format (click element #47) doesn't map to stable Playwright selectors. The element indices change every page load. The meta-agent, reading the action log's extracted_content field (e.g., "Clicked button 'Continue'"), can produce durable selectors like page.locator('button:has-text("Continue")').

5 render_report.py — HTML Report 475 lines

Generates a self-contained HTML report with all images and video base64-embedded. Open it in any browser, no server needed. Features: tabbed navigation (Session / Steps / Screenshots / Root Cause / Playwright Test), a screenshot lightbox with keyboard nav, and a dark theme matching GitHub's aesthetic.
