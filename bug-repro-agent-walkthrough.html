Browser-Use Hackathon · July 4, 2026 · Bengaluru

Give it a bug report. It reproduces the bug in a real browser.

repro-agent reads a GitHub issue, drives Chrome through the reproduction steps, and posts evidence back to the issue. One generic prompt handles any bug.

Python browser-use Claude Sonnet 4 Playwright Docker

Background

Plane is an open-source project tracker competing with Jira and Linear. It has 791 open issues, 289 of them bugs. Many include clear reproduction steps. Maintainers still walk through each one by hand: launch the app, click through menus, type the right input, observe the failure. That takes 5–15 minutes per issue and produces nothing reusable.

Core insight
The reproduction plan is already written in the bug report. An LLM reads those steps, drives a browser, and reports what it sees. No per-issue scripting.

repro-agent takes a GitHub issue URL, fetches the bug report, injects it into a generic prompt template, and launches a browser automation agent. The LLM figures out the clicks. Output: screenshots, action log, structured verdict, Playwright regression test, and a report posted back to the issue.

The reproducer constraint

The agent never proposes patches, never edits source code, never says "FIXED." It executes the reported steps, captures what happens, and tells you whether the bug is real. Reproduction and repair need different skills. Mixing them weakens both.

VerdictMeaningExit code
REPRODUCEDThe reported bug behavior was observed0
NOT_REPRODUCEDFeature worked correctly, bug not confirmed1
INCONCLUSIVEEvidence ambiguous, can't confirm or deny2
Observation-only constraint
The verdict reports what the agent saw. It does not judge whether the behavior is correct. That separation keeps the system useful even when a bug turns out to be "working as designed."

End-to-end sequence for a single reproduction run

Artifacts are saved before the browser closes. browser.close() can hang when Chrome is unresponsive, but the agent history is already in memory. Saving first means a crashed browser still produces full evidence.

Verdict parsing

scripts/drive.py 
VERDICT_PATTERN = re.compile(
    r"VERDICT:\s*(REPRODUCED|NOT_REPRODUCED|INCONCLUSIVE)\s*\|\s*(.+)",
    re.IGNORECASE,
)

One regex. The prompt tells the agent the exact format. The regex finds it or defaults to INCONCLUSIVE. No per-issue matchers, no NLP.

Code walkthrough

Five Python scripts, each with one job. No classes, no framework. You read each file top to bottom.

drive.py

One script does everything: fetch, prompt, drive, parse, save. Each phase depends on the previous one's output. The prompt needs the issue body. The agent needs the prompt. Artifacts need the history object. Splitting them into separate files would add wiring without adding clarity.

CDP auto-discovery · scripts/drive.py 
def discover_cdp_url(debug_port: int = 9222) -> str:
    """Auto-discover Chrome CDP browser-level WebSocket URL."""
    resp = urllib.request.urlopen(
        f"http://localhost:{debug_port}/json/version", timeout=3
    )
    data = json.loads(resp.read())
    return data["webSocketDebuggerUrl"]
The generic prompt · scripts/drive.py 
TASK_TEMPLATE = """Reproduce a bug in Plane.

## App
- URL: {plane_url}
- Credentials: {email} / <secret>
- Workspace: {workspace}

## Bug (issue #{number})
{title}
{body}

## Principles
- You are a reproducer, not a fixer.
- Navigate by URL when possible.
- Budget your steps.

## Verdict format
VERDICT: REPRODUCED | <what you saw>
VERDICT: NOT_REPRODUCED | <feature worked correctly>
VERDICT: INCONCLUSIVE | <why you couldn't determine>"""
The issue body is the plan
No per-issue scripting. The raw issue body becomes the reproduction plan. Claude Sonnet 4 parses informal bug reports into browser actions without additional structure.

Critical instructions go in extend_system_message, not the task prompt. browser-use compacts message history during long runs. The task prompt gets summarized. The system prompt stays intact. Action format, the one-action-per-step rule, and verdict formatting all need to survive compaction, so they live in the system prompt.

seed.py

Plane needs to be running with test data before the agent can reproduce anything. seed.py handles verification (check) and setup (populate) using only stdlib. No requests, no httpx. It authenticates via Plane's session cookie flow and talks to the internal Django API.

The seed data is intentionally crafted for edge cases:

Seed issuePurpose
Normal titleBaseline: verify standard flow works
"A" × 256Triggers the 255-char validation bug (#9329)
XSS in titleTests special character handling
Parent for sub-issuesTests hierarchy/expand UI
Cycle + module memberCross-feature testing
Fragile coupling
seed.py calls the same undocumented AJAX endpoints that Plane's React frontend uses. When Plane's API changes, seed.py breaks. Fine for a hackathon.

post_comment.py

Reads artifacts from reproductions/<N>/, builds a Markdown comment, and posts it via gh issue comment. The comment includes video, step trace, smoking-gun screenshot, root cause analysis, and the Playwright test.

Image hosting needs a workaround. GitHub comments strip local files. The script commits GIFs, video, and screenshots to the repro-agent repo, pushes, and references them via raw.githubusercontent.com URLs. mask_password() scrubs Plane credentials from every output before posting.

generate_playwright.py

Converts the action log into a skeleton Playwright test. The login fixture handles Plane's two-step email → password flow. Post-login steps become structured comments that the meta-agent rewrites into real selectors.

Two stages because browser-use actions reference element indices (click element #47) that change on every page load. The meta-agent reads extracted_content (e.g. "Clicked button 'Continue'") and writes durable selectors like page.locator('button:has-text("Continue")').

render_report.py

Generates a self-contained HTML report. All images and video are base64-embedded, so you open it in any browser without a server. Tabbed navigation, screenshot lightbox with keyboard controls, dark theme.

Live demo

One bug, three beats. Issue #9329: Plane's inline work item creation shows "Some error occurred" when the title exceeds 255 characters. The sidebar creation path shows a proper validation message for the same input. Two code paths, two different error messages. The agent finds this in 5 steps and 52 seconds.

Why this issue
Picked from 289 open bugs after filtering for browser-reproducibility, visual clarity, and step count. 5 steps, all basic browser actions (navigate, click, type, read toast). No special setup. The error is unambiguous on screen.

What happened
The agent typed a string one character over the limit. Plane's inline creation path catches the server-side 400 error but shows a generic toast. The sidebar creation path shows "Title should be less than 255 characters." Same validation, different error messages.
