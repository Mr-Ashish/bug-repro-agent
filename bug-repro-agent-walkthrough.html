Browser-Use Hackathon · July 4, 2026 · Bengaluru

Point it at a bug report. Watch it reproduce — live.

repro-agent reads any GitHub issue, drives a real browser through the reproduction steps, and posts evidence back. No hardcoded logic. One generic prompt. Full artifact chain.

Python browser-use Claude Sonnet 4 Playwright Docker

Background

Plane — an open-source project tracker competing with Jira and Linear — has 791 open issues, 289 of which are bugs. Many come with clear reproduction steps. But maintainers still walk through each one by hand: launch the app, click through menus, type the right input, observe the failure. That loop takes 5–15 minutes per issue and produces no reusable artifact.

Core insight
A bug report already contains the reproduction plan in natural language. An LLM can read those steps, drive a browser, and report what it sees — no per-issue scripting needed.

That's what repro-agent does. Given a GitHub issue URL, it fetches the bug report, injects it into a generic prompt template, launches a browser automation agent, and lets the LLM figure out the steps. The output: screenshots, an action log, a structured verdict, a Playwright regression test, and a rich report posted back to the issue.

The reproducer constraint

This agent never proposes patches, never edits source code, never says "FIXED." Its job is strictly observational: execute the reported steps, capture what happens, tell you whether the bug is real. This constraint exists because reproduction and repair require fundamentally different capabilities — conflating them produces neither well.

VerdictMeaningExit code
REPRODUCEDThe reported bug behavior was observed0
NOT_REPRODUCEDFeature worked correctly — bug not confirmed1
INCONCLUSIVEEvidence ambiguous — can't confirm or deny2
Why this matters
By constraining the agent to observation-only, the verdict is a fact claim about what the agent saw — not a judgment about correctness. This makes the system useful even when the bug turns out to be "working as designed."

Architecture

How does data flow from a GitHub issue URL to a posted verdict?

Four layers, each with a distinct responsibility. The key design decision: only one layer reasons about the bug. Everything else is infrastructure.

Architectural bet
drive.py doesn't know what the bug is. It plumbs the issue text into a prompt and saves whatever comes back. This means the system works on any issue without modification.

End-to-end sequence for a single reproduction run

Artifacts are saved before the browser is closed. This is intentional — browser.close() can hang if Chrome is unresponsive, but the agent history is already in memory. Artifacts survive crashes.

How does the verdict get parsed?

scripts/drive.py 
VERDICT_PATTERN = re.compile(
    r"VERDICT:\s*(REPRODUCED|NOT_REPRODUCED|INCONCLUSIVE)\s*\|\s*(.+)",
    re.IGNORECASE,
)

One regex. The agent is told the exact format to use, and the regex either finds it or defaults to INCONCLUSIVE. No per-issue matchers, no NLP.

Code walkthrough

Five Python scripts, each with a single job. No classes to instantiate, no framework — just functions you can read top to bottom.

drive.py — the brain

One script does everything: fetch, prompt, drive, parse, save. Why not a pipeline? Because each phase depends on the previous one's output — the prompt needs the issue body, the agent needs the prompt, artifacts need the history object. For a hackathon, colocation beats modularity.

CDP auto-discovery · scripts/drive.py 
def discover_cdp_url(debug_port: int = 9222) -> str:
    """Auto-discover Chrome CDP browser-level WebSocket URL."""
    resp = urllib.request.urlopen(
        f"http://localhost:{debug_port}/json/version", timeout=3
    )
    data = json.loads(resp.read())
    return data["webSocketDebuggerUrl"]
The generic prompt · scripts/drive.py 
TASK_TEMPLATE = """Reproduce a bug in Plane.

## App
- URL: {plane_url}
- Credentials: {email} / <secret>
- Workspace: {workspace}

## Bug (issue #{number})
{title}
{body}

## Principles
- You are a reproducer, not a fixer.
- Navigate by URL when possible.
- Budget your steps.

## Verdict format
VERDICT: REPRODUCED | <what you saw>
VERDICT: NOT_REPRODUCED | <feature worked correctly>
VERDICT: INCONCLUSIVE | <why you couldn't determine>"""
The issue IS the plan
No per-issue scripting. The raw issue body becomes the reproduction plan. This works because modern LLMs are surprisingly good at parsing informal bug reports into actionable steps.

Critical instructions live in extend_system_message rather than the task prompt. browser-use compacts message history during long runs — the task prompt gets summarized, but the system prompt stays intact. Action format references, the one-action-per-step rule, and verdict formatting must survive this compaction.

seed.py — environment readiness

Before the agent can reproduce anything, Plane needs to be running with test data. seed.py handles both verification (check) and setup (populate) using only stdlib — no requests, no httpx. It authenticates via Plane's session cookie flow and talks to the internal Django API.

The seed data is intentionally crafted for edge cases:

Seed issuePurpose
Normal titleBaseline — verify standard flow works
"A" × 256Triggers the 255-char validation bug (#9329)
XSS in titleTests special character handling
Parent for sub-issuesTests hierarchy/expand UI
Cycle + module memberCross-feature testing
Fragile coupling
seed.py talks to Plane's internal API — the same undocumented AJAX calls the React frontend makes. If Plane's API changes, seed.py breaks. Acceptable for a hackathon, not for production.

post_comment.py — GitHub reporter

Reads every artifact from reproductions/<N>/, builds a rich Markdown comment, and posts it via gh issue comment. Includes embedded video, step trace table, smoking-gun screenshot, root cause analysis, and the Playwright test.

The trickiest part: image hosting. GitHub comments can't embed local files. The script commits GIF, video, and evidence screenshot to the repro-agent's own repo, pushes to GitHub, and uses raw.githubusercontent.com URLs. Every image is permanently linked. The mask_password() function runs on every output — Plane credentials never appear in the posted comment.

generate_playwright.py — test generator

Converts the action log into a skeleton Playwright test. The login fixture works out of the box (handles Plane's two-step email → password flow). Post-login steps are dumped as structured comments — the meta-agent rewrites them into real selectors.

This two-stage approach exists because browser-use's action format (click element #47) doesn't map to stable Playwright selectors. The element indices change every page load. The meta-agent reads extracted_content (e.g. "Clicked button 'Continue'") and produces durable selectors like page.locator('button:has-text("Continue")').

render_report.py — HTML report

Generates a self-contained HTML report with all images and video base64-embedded. Open it in any browser, no server needed. Tabbed navigation, screenshot lightbox with keyboard nav, and a dark theme matching GitHub's aesthetic.

Demo walkthrough

Three beats, ~4 minutes total. Star issue: #9329 — inline work item creation shows a generic error when the title exceeds 255 characters. Fast, visual, always reproduces.

1

Live reproduction

~2 min

Run the command live. Audience watches Chrome move autonomously — navigating to Plane, logging in, finding the issues list, typing a 256-char title, observing the error toast.

Terminal 
python scripts/drive.py \
  --url https://github.com/makeplane/plane/issues/9329 \
  --context reproductions/9329/context.txt

Completes in ~43 seconds, 4 steps. Real-time progress in terminal.

2

Evidence inspection

~1 min

Open reproductions/9329/report.html in a browser. Walk through the tabs: session video, step-by-step action log, the smoking-gun screenshot showing the generic error toast, and the auto-generated Playwright test.

3

GitHub report

~30s

Post the rich reproduction report back to the original GitHub issue:

Terminal 
python scripts/post_comment.py --issue 9329 \
  --evidence reproductions/9329/evidence-03.png

Includes inline video, step trace, evidence screenshot, root cause, and Playwright test.

The punchline
The same command works on any of the 289 bug issues. No per-issue scripting. The template is generic; the LLM adapts. That's the value proposition.
